# Statement library

Original bank statements a merchant uploads, kept privately beside the
account and period they say it covers. Everything CoinPay knows about one of
these files is what the user entered plus the bytes. Nothing is extracted
into the ledger, and nothing about the issuer is verified. The product
label is **Imported bank statement — user supplied**, everywhere.

This is the counterpart to [FINANCES-REPORTS.md](./FINANCES-REPORTS.md): a
report is generated by CoinPay; a statement is supplied by the user. Neither
is called official.

## Import

`POST /api/finances/statements` (multipart) or

```bash
coinpay finances statements import ./bank-august.pdf --account acct_123 --period 2026-08 --timezone America/Los_Angeles
coinpay finances statements import ./card-cycle.pdf --account acct_456 --from 2026-08-14 --to 2026-09-14 --institution "Example Bank"
```

Fields: `file`, `accountId` (must be owned), `period` or `from`+`to` (`to`
exclusive, so an issuer cycle that is not a calendar month is supported),
optional `timezone`, `institutionLabel`, `cycle` (`monthly` / `quarterly` /
`custom`), `notes`.

Before anything is stored the file is inspected:

- size at most 25 MiB (`FINANCES_STATEMENT_MAX_BYTES` can lower it);
- `%PDF-` header and a trailer;
- not encrypted — a password-protected PDF is refused with an explanation;
  CoinPay never asks for the bank password;
- no active content. Raw bytes and every Flate-compressed stream are scanned
  for JavaScript, launch/open actions, embedded files, XFA forms, remote
  go-to and form-submission actions. Any of these refuses the file with the
  reason.

A file that fails inspection is not stored at all; there is no downloadable
quarantined state. A file that passes is recorded `scan_state = clean`.

Duplicate handling is per merchant: identical bytes already associated with
the same account and period return the existing record; identical bytes for
a different account or period create a separate record and say
`duplicateOf`. A matching hash proves the bytes are the same, not that the
bank issued them.

## Fetching from the banks

SimpleFIN supplies balances and transactions, never the PDFs: the protocol
has no document endpoint and the Bridge keeps none. So the CLI downloads them
from each bank itself, **on the merchant's own machine**, and imports each one
through the endpoint above:

```bash
coinpay finances statements banks            # linked banks: signed in here? last fetch?
coinpay finances statements login chase      # once per bank, in a window
coinpay finances statements fetch            # every new statement, every signed-in bank
coinpay finances statements fetch citi --since 2026-01 --headed
coinpay finances statements assist dcu       # a window; every PDF you download is imported
coinpay finances statements coverage         # which account-months have a statement
coinpay finances statements runs|local|retry
```

- **Sessions stay local.** Each bank gets its own Chrome profile under
  `~/.coinpay/statements/profiles/<bank>` (`COINPAY_STATEMENTS_DIR` moves it),
  signed in by a person in a real window. CoinPay never asks for or receives a
  bank password, cookie or page. While the login window is open, go on to the
  page that lists statements before closing it: that page is where `fetch`
  starts from then on, so a bank with no built-in entry works the same way.
- **What fetch clicks.** Headless by default. It follows the page's
  "Statements" link when the list is not there yet, and clicks each control in
  a dated row that reads like a download (`Download`, `PDF`, `View statement`,
  a `.pdf` link), pressing a dialog's `Download` button when a click opens one.
  Preference, paperless and tax-form links are left alone.
- **Filing.** The account is the one whose last four digits appear in the row
  or file name (or the bank's only account); the period is the cycle the row
  prints, imported as `--from/--to` with `cycle=custom`, else the closing
  month. A copy of every file stays in `~/.coinpay/statements/files`; one that
  cannot be placed is kept there and reported as unmatched (`statements
  local`, then import it by hand or `statements retry`). A row already
  fetched is never clicked again, and identical bytes are never imported twice.
- **Runs are reported.** After each bank, the CLI posts counts only to
  `POST /api/finances/statements/fetch-runs` (`ok`, `login_needed`,
  `no_statements`, `error`; no URL or content). `GET
  /api/finances/statements/coverage?months=12` combines those with the library:
  per account, each month is `have`, `missing` or `open` (the current month),
  by the month the statement closed in. The PWA shows both on
  `/finances/statements`.
- **Unattended.** `fetch` exits `3` when any bank needs a sign-in or showed no
  statements, so a weekly cron entry can tell you:
  `30 7 * * 1 coinpay finances statements fetch`.
- **Agents.** `coinpay mcp` serves the same over MCP (stdio):
  `statements_coverage`, `statements_fetch_runs`, `statements_banks`,
  `statements_list`, `statements_fetch` (runs a fetch on this machine) and
  `finance_accounts`. `claude mcp add coinpay -- coinpay mcp`.

Bank pages change without notice; nothing here depends on one bank's markup,
and when the finder sees no statements it says so rather than guessing.
`statements assist` is the fallback. Requires Node 22+ and a Chrome or
Chromium (`CHROME_PATH`).

## Storage

Bytes go to the private volume (`FINANCES_FILES_DIR`, `/mnt/files/finances`
on Railway) encrypted with AES-256-GCM under a documents-only key
(`FINANCES_DOCUMENTS_KEY`, or HKDF over `ENCRYPTION_KEY`). Object keys are
`statements/<merchant>/<uuid>`, so no path can be built for another
tenant's file. Writes are staged and renamed; the plaintext SHA-256 is
recorded and verified on every download. Every replica that serves
downloads must mount the same volume.

## Download

`GET /api/finances/statements/:id/download` answers the original bytes as
an attachment with `Cache-Control: no-store`, `nosniff` and a sandboxing
CSP. Ownership is rechecked on every request. There are no public or
durable bearer links, and the PWA never embeds the PDF inline.

```bash
coinpay finances statements download stmt_123 --output ./original.pdf
```

## Reconciliation

A statement can be checked against one **immutable report revision** that
covers the same account, period and currency:

```text
expected closing = entered opening + sum(posted signed transaction amounts)
difference       = entered closing - expected closing
```

```bash
coinpay finances statements reconcile stmt_123 --report report_123 --opening 1200.00 --closing 1450.25 --currency USD
coinpay finances statements reconcile stmt_456 --report report_456 --opening 812.10 --closing 903.55 --currency USD --liability-positive --acknowledge
```

All arithmetic is exact decimal. The values as typed are stored alongside
the normalised ones. `--liability-positive` (`signConvention:
"liability_positive"`) is for credit-card statements that print what is
owed as a positive number; the ledger stores liabilities negative, so the
entered balances are negated before comparison.

Outcomes: `matched` (zero difference), `user_reconciled` (zero difference
plus `--acknowledge`), `mismatch`, `unavailable` (evidence missing). None of
these is `bank_verified`; the check confirms the arithmetic against the
frozen dataset, not that every transaction identity was compared. A new
report revision or a deleted statement invalidates the result; the report's
`reconciliation_status` moves with it. The CLI exits `3` on a mismatch.

## Deletion

`DELETE /api/finances/statements/:id` (CLI: `statements delete <id> --yes`)
removes the stored bytes and retires the metadata. Reconciliation evidence
built on it becomes `unavailable`. Synced transactions are untouched.

This is distinct from disconnecting a provider (credential removed, history
kept) and from deleting a connection (accounts, transactions, statements and
reconciliations under it are removed after an explicit confirmation that
lists them). Deleted files leave the live volume immediately; backups
follow the deployment's retention window.

## Audit

Imports, downloads, reconciliations and deletions are recorded in
`finance_audit_events` with ids, byte counts and states only — never
balances, descriptions or file names.
