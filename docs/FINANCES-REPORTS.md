# Finance reports

Monthly, quarterly and custom-period activity reports over the bank and card
accounts a merchant has linked under `/finances`. A report is generated by
CoinPay from imported account data. It is not an institution-issued statement,
and every surface that shows one says so.

Three things stay separate:

| Item | Meaning | Label |
|---|---|---|
| Synced financial data | Rows fetched from SimpleFIN or Plaid | Bank activity |
| CoinPay-generated document | A report calculated from retained rows | Monthly / Quarterly activity report |
| Uploaded institution document | A PDF the user supplied | Imported bank statement — user supplied |

See [STATEMENTS.md](./STATEMENTS.md) for the third.

## What a report is

A report is an **immutable snapshot**. When it is generated, the selected
rows are taken by one SQL statement (`finance_report_dataset()`), which
means the rows, their count and their per-currency totals all describe the
same Postgres snapshot. The totals are summed as `numeric` in the database
and re-summed in exact decimal arithmetic on the way out; if the two
disagree the report fails rather than ships. Nothing in a report is computed
with floating point.

The snapshot is stored as the report's canonical dataset. PDF, HTML, CSV and
JSON are all rendered from it. Re-running the same selection after new rows
arrive creates a **new revision** and marks the old one superseded; the old
one is never edited.

Every report carries three independent facts:

- `local_export_complete` — every row the snapshot selected is in the export.
  A count mismatch fails the report; it is never a footnote.
- `provider_coverage` — `unknown`, `partial`, or `available_window_fetched`.
  Derived from **what was asked of the provider**, not from the data: a month
  with a clean fetch window and no rows is `available_window_fetched`; a month
  nobody fetched is `unknown`, however many rows it happens to hold.
  `available_window_fetched` is not a claim that the institution supplied
  complete history.
- `reconciliation_status` — `not_attempted`, `unavailable`, `mismatch` or
  `user_reconciled`. Set only through a statement reconciliation.

Other guarantees:

- Periods are calendar periods in a stored IANA timezone, `[start, end)`.
  A transaction posted at exactly the end instant belongs to the next period.
  Quarters are 90, 91 or 92 days, never "90 days".
- A running period is labelled **Period to date** and its effective end is
  the snapshot cutoff. Wholly future periods are rejected.
- Currencies are never combined. Custom currency identifiers keep their
  exact value and case.
- Credits and debits are gross bank flows. Nothing calls a credit revenue.
- Opening and closing balances are `unavailable` unless entered from a
  statement. The provider's current balance is shown with its own timestamp
  and is never labelled a closing balance.
- Pending items sit in an appendix and are excluded from every total. A
  pending item with no posting date is stored with a null `posted`, not
  1970 and not today.

## Timezone

Calendar boundaries are resolved in the merchant's saved finance timezone
(`finance_settings.timezone`). When none is saved, the first request must
pass one and it is remembered; the server never falls back to its own zone.
Abbreviations such as `EST` are refused.

## Coverage and backfills

Reports do not call the provider. Coverage is read from
`finance_fetch_windows`, which records every interval ever requested per
account and what came back (rows, rejected rows, provider warnings, whether
the bridge cut the range short). To fill history, queue a **backfill**: the
period is planned into calendar-month chunks with a five-day overlap, none
longer than 45 days, and a durable job fetches them one at a time.

Provider requests are budgeted per credential: 20 per rolling 24 hours, of
which background work may use 16. Interactive `Sync now` keeps the other
four. When the budget is gone the job parks as `waiting_for_budget` with a
next-attempt time; nothing retries with payment or a second credential. A
provider `402` is surfaced as `provider_payment_required` and is the
merchant's subscription to sort out with the bridge.

Jobs live in `finance_jobs`. A worker claims one with `finance_claim_job()`
(`FOR UPDATE SKIP LOCKED`) and gets a `lease_version`; every later write
carries that version, so a worker that stalls and wakes cannot commit over
the one that took over. Progress is recorded per chunk and ingestion is
idempotent, so a crash mid-backfill costs at most one repeated request and
never a duplicate row.

The worker runs inside the Next.js server (started from
`src/instrumentation.ts` when `ENABLE_BACKGROUND_MONITOR=true`, or always
with `FINANCES_WORKER_ENABLED=true`). A scheduler can drive it instead by
POSTing `/api/cron/finance-worker` with the cron secret.

## API

All routes are under `/api/finances`, merchant-authenticated (session JWT or
`token` cookie; payment API keys are refused). Cookie-authenticated writes
must be same-origin. Every response is `Cache-Control: no-store`.

| Method and route | Purpose |
|---|---|
| `POST /sync-jobs` | Queue a backfill (`{kind:"backfill", period\|from+to, timezone?, connectionId?}`) or refresh. `202`. |
| `GET /jobs`, `GET /jobs/:id`, `POST /jobs/:id/cancel` | Job history, progress, cancellation. |
| `GET /coverage?period=…` | Per-account coverage for an interval. |
| `POST /reports` | Create a revision. `202` with `report` and `job`. |
| `GET /reports`, `GET /reports/:id` | History and one report's metadata, totals, warnings, artifacts. |
| `GET /reports/:id/download?format=pdf\|html\|csv\|json` | Bytes as an attachment; `409` until ready. |
| `DELETE /reports/:id` | Remove dataset and files. Source rows stay. |
| `POST /connections/:id/consent` | `{dailySync: boolean}` — opt into a once-daily background sync. |
| `POST /connections/:id/disconnect` | Remove the credential and cancel work; keep history. |
| `DELETE /connections/:id` | Destructive; requires `X-Confirm-Delete: yes` and lists what goes. |

Creation requests accept an `Idempotency-Key` header. New routes answer
errors as `{ "error": { "code", "message", "retryable", "jobId"? } }`.

Example:

```json
POST /api/finances/reports
{
  "period": "2026-Q2",
  "timezone": "America/Los_Angeles",
  "accountIds": ["<owned-account-uuid>"],
  "scope": "business",
  "formats": ["pdf", "csv", "json"],
  "includePendingAppendix": true,
  "strict": false
}
```

`strict` fails the report unless `provider_coverage` is
`available_window_fetched` and there are no warnings.

## CLI

```bash
coinpay login                                   # merchant session; API keys are refused
coinpay finances connect --provider simplefin   # token prompted without echo
coinpay finances connect --provider simplefin --setup-token-stdin < token.txt
coinpay finances consent conn_123 on            # daily background sync

coinpay finances backfill --period 2026-Q2 --timezone America/Los_Angeles --wait --json
coinpay finances jobs get job_123 --json        # no provider request
coinpay finances coverage --period 2026-08

coinpay finances report --period 2026-08 --account acct_123 --format pdf --output ./2026-08.pdf
coinpay finances report --period 2026-Q2 --scope business --format csv --output ./2026-Q2.csv
coinpay finances report --from 2026-04-01 --to 2026-07-01 --format json --output ./q2.json   # --to is exclusive
coinpay finances reports list
coinpay finances reports download rep_123 --format html --output ./rep.html
coinpay finances reports delete rep_123 --yes

coinpay finances disconnect conn_123 --yes      # history kept
```

Flags: `--json` (stdout is only the result; progress on stderr), `--wait`,
`--output` (implies waiting), `--overwrite`, `--strict`, repeated or
comma-separated `--account`, `--scope`, `--timezone`, `--hidden`.

Exit codes for the new subcommands: `0` done or job accepted, `2` invalid
input, `3` strict rejection, `4` authentication, `5` provider/storage
failure. Legacy subcommands keep their exit behaviour. Downloads are written
atomically with mode `0600` and never overwrite without `--overwrite`.
Nothing is auto-opened.

## Storage and configuration

| Setting | Default | Meaning |
|---|---|---|
| `FINANCES_FILES_DIR` | `/mnt/files/finances` when the volume exists, else `./.data/finances` | Private store for artifacts and statements. Must be shared by every replica that serves downloads. |
| `FINANCES_DOCUMENTS_KEY` | derived from `ENCRYPTION_KEY` via HKDF | AES-256-GCM key for stored files; distinct from the credential key. |
| `FINANCES_REQUEST_BUDGET` / `FINANCES_BACKGROUND_BUDGET` | 20 / 16 | Per-credential requests per 24 h. |
| `FINANCES_SIMPLEFIN_ALLOWED_HOSTS` | `beta-bridge.simplefin.org,bridge.simplefin.org` | Hosts a claim or access URL may point at. Everything else, including any IP literal, is refused before credentials are sent. |
| `FINANCES_PDF_MAX_ROWS` | 20000 | Rows the PDF ledger carries before switching to an excerpt; CSV/JSON always hold every row. |
| `FINANCES_REPORTS_ENABLED`, `FINANCES_STATEMENT_IMPORTS_ENABLED`, `FINANCES_SCHEDULED_SYNC_ENABLED` | on | Emergency switches. Setting one to `false` stops new work; nothing is dropped. |
| `FINANCES_WORKER_ENABLED` | follows `ENABLE_BACKGROUND_MONITOR` | In-process worker loop. |

If a download-serving replica lacks an artifact file, the file is re-rendered
from the frozen dataset; CSV/JSON are checked against the recorded hash.

Deleting a report removes its files and dataset. Backups follow the
deployment's normal retention; removal from immutable backups is not instant.

## Schema

Added by `supabase/migrations/20260912120000_finances_reports_statements.sql`:
`finance_settings`, `finance_source_connections`, `finance_transaction_revisions`,
`finance_balance_snapshots`, `finance_jobs`, `finance_request_usage`,
`finance_fetch_windows`, `finance_reports`, `finance_report_artifacts`,
`finance_statements`, `finance_reconciliations`, `finance_audit_events`, plus
columns on the existing three tables. Accounts are now unique on
`(source_connection_id, external_id)`; every existing account was moved in
place under a `legacy` source with its uuid intact. Migrations are applied
to production through the Supabase MCP, not CI.
